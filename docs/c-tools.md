# 🛠️ C Development & Debugging Tools 가이드

> 리눅스 터미널 환경에서의 효율적인 C 언어 개발과 메모리 관리를 위해 스터디에서 공식적으로 활용하는 도구들의 사용법을 정의합니다.

---

## 1. 코드 탐색 기본: ctags

`ctags`는 프로젝트 내의 함수, 변수, 매크로 등의 정의 위치를 인덱싱하여 빠르게 이동할 수 있게 해주는 기본 내비게이션 툴입니다.

### 📌 태그 생성

프로젝트 루트 디렉토리에서 아래 명령어를 실행하여 tags 파일을 생성합니다.

```bash
ctags -R *
```

### 📌 Vim에서의 활용 (기본 점프)

* `Ctrl` + `]` : 커서가 위치한 함수/구조체/매크로의 정의부로 이동
* `Ctrl` + `t` : 이동하기 이전 위치로 복귀 (스택처럼 쌓이므로 여러 번 점프 후 순차적으로 돌아올 수 있습니다)

---

## 2. 코드 탐색 심화: cscope (Advanced)

`ctags`가 단순히 '정의'를 찾아준다면, `cscope`는 "이 함수가 어디서 호출되었나?", "이 변수가 참조된 모든 곳은?"과 같은 교차 참조(Cross-Reference) 분석을 제공하는 강력한 도구입니다.

### 📌 데이터베이스 생성

단순 빌드뿐만 아니라 검색 속도를 높이는 인덱스를 함께 생성합니다.

```bash
# -R: 하위 디렉토리 순회, -b: DB만 생성(TUI 미실행), -q: 빠른 검색을 위한 역방향 인덱스 생성
cscope -Rbq
```

(위 명령어를 실행하면 cscope.out, cscope.in.out, cscope.po.out 파일이 생성됩니다.)

### 📌 Vim에서의 활용 및 8가지 고급 검색 쿼리

Vim 내에서 명령어 모드(:)로 진입한 후 `cs find [질의어] [검색어]` 형태로 사용합니다.

| 질의어 | 단축 키워드 | 기능 설명 | 사용 예시 |
| :---: | :---: | :--- | :--- |
| `0` | `s` | **C 심볼 검색:** 변수, 함수, 매크로 등이 사용된 모든 위치 검색 | `:cs find s list_insert` |
| `1` | `g` | **정의부 검색:** (ctags와 동일) 해당 심볼이 정의된 곳으로 이동 | `:cs find g node_t` |
| `2` | `d` | **호출 함수 검색:** 이 함수가 내부적으로 호출하는 함수들 목록 | `:cs find d list_delete` |
| `3` | `c` | **역호출 함수 검색:** 이 함수를 호출하고 있는 모든 함수들 검색 | `:cs find c create_node` |
| `4` | `t` | **문자열 검색:** 소스 코드 내의 특정 텍스트/문자열 검색 | `:cs find t "Memory Leak"` |
| `6` | `e` | **정규식 검색:** egrep 패턴을 사용한 정규 표현식 검색 | `:cs find e ^[a-z]+_node` |
| `7` | `f` | **파일 검색:** 프로젝트 내의 파일 이름으로 검색 | `:cs find f list.c` |
| `8` | `i` | **Include 검색:** 특정 헤더 파일을 include 하고 있는 모든 파일 검색 | `:cs find i _internal.h` |

💡 팁: 검색 결과가 여러 개일 경우 하단에 리스트가 뜨며, 번호를 입력해 원하는 파일로 바로 점프할 수 있습니다.

## 3. 메모리 검증: Valgrind

C 언어 자료구조 구현 시 발생하는 90% 이상의 버그는 메모리(동적 할당 및 해제) 문제에서 비롯됩니다. PR을 올리기 전 Valgrind 통과는 필수입니다.

### 📌 엄격한 메모리 누수 검사

컴파일 시 디버깅 심볼(-g)을 포함해야 정확한 라인 넘버가 출력됩니다.

```bash
valgrind --leak-check=full --show-leak-kinds=all --track-origins=yes ./bin/linkedlist_test
```

`--track-origins=yes` : 초기화되지 않은 값(Uninitialized value)이 정확히 어디서 생성되었는지 추적해줍니다.

### 🚨 Valgrind 주요 에러 메시지
* **definitely lost**: 메모리 포인터를 완전히 잃어버려 해제가 불가능한 명백한 누수 (수정 1순위)
* **Invalid read/write of size N**: 할당 범위를 넘어서거나, 이미 free()된 메모리에 접근 시도 (Segmentation fault의 직접적인 원인)
* **Conditional jump or move depends on uninitialised value(s)**: 쓰레기값(초기화되지 않은 변수)을 가지고 if문 등에서 분기 처리를 하려고 할 때 발생

## 4. 디버깅: GDB

Segmentation fault가 발생하거나 논리적 오류를 한 줄씩 추적해야 할 때 사용하는 디버거입니다.

## 📌 GDB 명령어

터미널 환경에서 소스 코드를 분할 화면으로 띄워놓고 직관적으로 디버깅할 수 있는 강력한 모드입니다.

| 명령어 (단축) | 기능 설명 |
| :--- | :--- |
| `break [함수명/라인]` (`b`) | 특정 함수나 줄 번호에 중단점(Breakpoint) 설정 |
| `run` (`r`) | 프로그램 실행 |
| `next` (`n`) | 다음 줄로 이동 (함수 안으로 들어가지 않음) |
| `step` (`s`) | 다음 줄로 이동 (함수가 있으면 함수 내부로 진입) |
| `print [변수명]` (`p`) | 현재 변수의 값 또는 구조체 데이터 출력 (예: `p node->data`) |
| `continue` (`c`) | 다음 중단점을 만날 때까지 프로그램 계속 실행 |
| `backtrace` (`bt`) | 프로그램이 죽었을 때, 역추적하여 어떤 함수 호출 경로에서 죽었는지 콜스택 확인 |
| `layout src` | TUI 모드: 소스 코드 창 띄우기 |
| `layout asm` | TUI 모드: 어셈블리어 창 띄우기 |
| `layout regs` | TUI 모드: CPU 레지스터 창 띄우기 |
| `Ctrl + l` | TUI 모드: 화면 출력 깨짐 발생 시 레이아웃 새로고침(리프레시) |
| `quit` (`q`) | GDB 종료 |
