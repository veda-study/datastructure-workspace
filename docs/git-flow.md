# 🌿 Git-Flow 전략 및 커밋 컨벤션

> 본 문서는 VEDA C Data Structure ADT 프로젝트의 원활한 협업을 위한 브랜치 운영 전략과 커밋 메시지 작성 규칙을 정의합니다.

## 1. 브랜치 전략 (Git-Flow 기반)

우리 스터디는 단순화된 Git-Flow 모델을 채택하여 다음 3가지 핵심 브랜치를 운영합니다.

* **`main`**: 언제든 실행 가능한 안정적인 배포(Release) 버전의 소스코드가 위치하는 브랜치입니다. (직접 Commit 금지)
* **`develop`**: 다음 출시 버전을 개발하기 위해 각 기능들이 병합(Merge)되는 통합 브랜치입니다. 기본적으로 이 브랜치를 기준으로 작업이 파생됩니다.
* **`feat/...`**: 새로운 기능 개발을 위해 `develop` 브랜치에서 파생되는 브랜치입니다. 기능 개발이 완료되면 `develop`으로 PR(Pull Request)을 보냅니다.
  * **브랜치 명명 규칙:** `feat/[키값]-기능명`
  * 예시: `feat/[VDS-5]-stack-push`

### 🔄 작업 흐름 (Workflow)
1. `develop` 브랜치에서 최신 상태를 `pull` 받습니다.
2. `develop` 브랜치에서 새로운 `feat/...` 브랜치를 생성하고 이동합니다.
3. 기능 개발 완료 후 원격 저장소에 `push` 합니다.
4. Github에서 `feat/...` -> `develop`으로 Pull Request를 생성하고 코드 리뷰를 받습니다.
5. 리뷰 승인(Approve) 후 `develop`에 병합(Merge)합니다.

## 2. 커밋 메시지 컨벤션

모든 커밋 메시지는 Jira 이슈 트래킹 및 가독성을 위해 아래의 형식을 엄격히 따릅니다.

### 📝 커밋 메시지 포맷
```text
커밋타입: [이슈번호] 작업 내용 요약
(빈 줄)
상세 작업 내용 (선택 사항)
```

### 🏷️ 커밋 타입 (Commit Type)
* `feat:` : 새로운 기능 추가 (예: 삽입, 삭제 함수 구현)
* `update:` : 기존 로직 수정 및 개선 (버그는 아니지만 구조나 흐름을 변경할 때)
* `fix:` : 버그 수정 (컴파일 에러, Segmentation Fault 등)
* `docs:` : 문서 작성 및 수정 (`README.md`, 주석 추가 등)
* `refactor:` : 코드 리팩토링 (기능 변화 없이 코드 구조 개선, 변수명 변경 등)
* `test:` : 테스트 코드 작성 및 수정
* `chore:` : 빌드 환경 설정, Makefile 수정, 잡무 등

### ✅ 커밋 메시지 작성 예시
```plaintext
feat: [VDS-05] 연결 리스트 삽입 기능 구현
```

## 3. Pull Request (PR) 컨벤션

코드 리뷰를 원활하게 진행하기 위해 PR 생성 시 다음 양식과 규칙을 준수합니다.

### ⚙️ PR 기본 설정 규칙
* **Base Branch**: `develop` (방향: `feat/...` ➡️ `develop`)
* **Assignees** (담당자): PR을 올리는 본인을 할당합니다.
* **Reviewers** (리뷰어): 현재 해당 자료구조 프로젝트를 함께 진행 중인 팀원 모두를 할당합니다.

### 📝 PR 메시지 템플릿 (본문)

Github에서 PR 생성 시 본문에 아래의 템플릿을 복사하여 작성합니다.

```Markdown
## 📌 관련 Jira 이슈
* 연동 이슈: [VDS-5]

## 📝 접근 방식
* (예시) 파수꾼 노드(Sentinel Node)를 활용하여 분기문을 최소화하는 방식으로 삽입 로직을 구현했습니다.
* (예시) `is_empty()` 헬퍼 함수를 static으로 만들어 내부적으로 사용했습니다.

## ⚠️ 고민했던 점 및 질문
* (예시) 노드 삭제 시 메모리 해제(`free`) 순서가 헷갈렸는데, 이 부분에 누수가 없는지 꼼꼼히 리뷰 부탁드립니다!
* (예시) 변수명을 `curr`로 할지 `temp`로 할지 고민하다 `curr`로 적용했는데 어떤가요?
```
